# Архитектура Receipt Tracker

Базовый контекст на 9 ноября 2026 года. Документ разделяет реализованный каркас, принятые решения и планы. Актуальное поведение проверяется по коду.

## Назначение

Учёт личных расходов по фотографиям чеков через Telegram.

Планируемый MVP: пользователь отправляет фото → Telegram передаёт обработку Core → Core организует OCR и создаёт черновик → пользователь исправляет и подтверждает → Core сохраняет расходы в PostgreSQL.

Этот сценарий ещё не реализован. Аналитика, общий каталог товаров, сравнение цен, внешнее обогащение и векторный поиск — дальнейшие направления, не обязательные части текущего каркаса.

## Принятые решения

| Область                    | Решение                                               |
| -------------------------- | ----------------------------------------------------- |
| Backend                    | TypeScript, NestJS 12                                 |
| HTTP                       | Fastify                                               |
| Репозиторий                | NestJS-монорепозиторий с приложениями Core и Telegram |
| Пакетный менеджер и сборка | pnpm, Rspack через Nest CLI                           |
| База и ORM                 | PostgreSQL, TypeORM                                   |
| Application-слой           | Сервисы, без отдельных Use Case-классов на старте     |
| Логирование                | Встроенный Logger NestJS                              |
| Линтер и форматтер         | Oxlint, Prettier                                      |

Snaptix — образец организации кода. Его Express, Prisma, CQRS, Gateway и транспортные решения не являются требованиями Receipt Tracker.

## Границы приложений

- **Telegram:** взаимодействие с пользователем через бота и передача запросов Core; прямое подключение к PostgreSQL не предусмотрено.
- **Core:** бизнес-модули, обработка чеков и расходов, технические интеграции и хранение данных через TypeORM.
- Транспорт Telegram → Core пока не выбран. Работающие HTTP-серверы не означают, что HTTP уже утверждён для общения приложений.

## Реализованный каркас

```text
receipt-tracker/
├── apps/
│   ├── core/src/
│   │   ├── core/
│   │   │   ├── config/
│   │   │   └── setup/settings/
│   │   ├── infrastructure/database/
│   │   ├── modules/
│   │   ├── app.module.ts
│   │   └── main.ts
│   └── telegram/src/
│       ├── core/
│       │   ├── config/
│       │   └── setup/settings/
│       ├── modules/tg/
│       ├── telegram.module.ts
│       └── main.ts
├── libs/common/
├── docs/
├── docker-compose.yml
└── nest-cli.json
```

- Оба приложения используют Fastify, собственный конфигурационный класс и локальный `initSetup`.
- Core подключает Swagger и shutdown hooks; Telegram — только shutdown hooks.
- Swagger: `/api`; OpenAPI JSON: `/api-json`. Это адреса документации, а не глобальный префикс бизнес-маршрутов.
- Core подключает `ConfigModule`, `CoreModule` и `InfrastructureModule → DatabaseModule`.
- TypeORM использует параметры окружения, `autoLoadEntities: true`, `synchronize: false` и SQL-логирование.
- PostgreSQL 17 описан в Compose; пароль берётся из переменной `POSTGRES_PASSWORD`.
- Контроллеры и сервисы пока шаблонные. Бизнес-сущности, репозитории и миграции не созданы.
- `libs/common` пока шаблонная. `libs/contracts` и `libs/core` не созданы; добавлять их следует по потребности.
- `@fastify/cookie` установлен, но не зарегистрирован. Глобальная валидация и CORS не настроены. ObserveModule не подключён.

## Будущие бизнес-модули

Модули создаются под реальную функциональность в `apps/core/src/modules/<feature>/`:

- `api` — контроллеры, входные DTO и валидация границы.
- `application` — сервисы и последовательность бизнес-операций.
- `domain` — бизнес-сущности, инварианты и правила.
- `infrastructure` — репозитории, TypeORM и технические интеграции модуля.

Договорённость — трёхслойная организация: presentation, application, data access. Папка `domain` выделяет бизнес-модель и сама по себе не вводит обязательную четырёхслойную чистую архитектуру.

Общая инфраструктура приложения находится в `src/infrastructure`, инфраструктура модуля — внутри модуля. Степень разделения доменных моделей и TypeORM entities пока не определена.

Не путать `apps/core` (бизнес-приложение), `apps/*/src/core` (технические настройки) и возможную будущую `libs/core` (общие технические компоненты).

## Открытые решения и отложенные задачи

- Транспорт Telegram → Core и механизм фоновой обработки.
- Telegram-библиотека, получение обновлений, аккаунт пользователя и авторизация.
- OCR-провайдер и хранение исходных изображений.
- Статусы чеков, дубли, повторные попытки, проверка сумм и подтверждение пользователем.
- Конкретные бизнес-модули, схема данных и стратегия миграций.
- Подход к валидации; cookies и CORS при появлении соответствующих сценариев.
- Отдельная тестовая БД и окружение Core e2e.

Это не список компонентов для немедленного создания. Обновляйте документ при принятии решений и изменении границ или структуры приложения.
