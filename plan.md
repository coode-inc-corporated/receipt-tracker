# План настройки CI/CD для тестового окружения

## 1. Цель

Настроить управляемую сборку и развёртывание одного выбранного микросервиса из комментария к pull request.

Целевой сценарий:

1. Разработчик пушит изменения в ветку этого репозитория.
2. Разработчик открывает pull request из этой ветки в любую другую ветку того же репозитория.
3. Участник репозитория оставляет в PR одну из команд:
   - `run build core`;
   - `run build telegram`.
4. GitHub Actions проверяет команду и права автора комментария.
5. GitHub Actions получает точный commit SHA исходной ветки PR.
6. Для выбранного микросервиса собирается Docker-образ.
7. Образ публикуется в Docker Hub в namespace `marianna2710`.
8. GitHub Actions подключается по SSH к тестовому серверу.
9. Docker Compose на сервере скачивает новый образ и обновляет выбранный сервис. Его зависимости, включая нужную базу данных, запускаются, если ещё не работают.
10. Результат выполнения публикуется в комментарии PR и остаётся в логах GitHub Actions.

## 2. Зафиксированные решения

- Используется одно общее тестовое окружение. Новый успешный деплой выбранного микросервиса обновляет это окружение.
- Одновременно развёртываемые preview-окружения для отдельных PR не создаются.
- На первом этапе разрешены только микросервисы `core` и `telegram`.
- Команды `run build all` и сборка нескольких сервисов одной командой не нужны.
- PR создаются только из веток текущего репозитория. Форки не поддерживаются.
- Команду может запускать любой действующий участник репозитория.
- Production/test Docker Compose хранится на сервере, а не управляется GitHub Actions как файл из репозитория.
- Рабочий каталог на сервере: `/home/buho`.
- В одном серверном Compose-файле описываются все микросервисы и базы данных.
- Специализированные HTTP health endpoints пока отсутствуют и в эту задачу не входят.
- Секреты не хранятся в репозитории, Docker-образах, Compose-файле или логах workflow.

## 3. Текущее состояние проекта

В репозитории уже есть:

- NestJS-монорепозиторий с приложениями `core` и `telegram`;
- команды `pnpm build:core` и `pnpm build:telegram`;
- `apps/core/Dockerfile`;
- `apps/telegram/Dockerfile`;
- локальный `docker-compose.yml` с сервисами `postgres`, `core` и `telegram`;
- PostgreSQL 17 с постоянным named volume;
- отключённый TypeORM `synchronize`.

Пока отсутствуют:

- workflow GitHub Actions;
- production/test Compose-конфигурация с образами из Docker Hub;
- зафиксированный контракт тегирования образов;
- GitHub Secrets и Variables для Docker Hub и SSH;
- документированная подготовка сервера и процедура отката.

Текущий корневой `docker-compose.yml` ориентирован на локальную разработку и использует `build:`. Серверному Compose требуется `image:` с опубликованными образами. Локальный Compose не следует автоматически заменять серверным вариантом: у них разные задачи.

## 4. Предлагаемая архитектура

### 4.1. Триггер

Workflow запускается только при создании нового комментария через событие `issue_comment`.

Особенность GitHub Actions: workflow для `issue_comment` должен уже находиться в default branch. Само событие работает в контексте default branch, поэтому нельзя использовать его `GITHUB_SHA` как SHA изменений из PR. Данные открытого PR и SHA его исходной ветки нужно отдельно запросить через GitHub API.

Workflow должен сразу завершаться без деплоя, если:

- комментарий оставлен не в pull request, а в обычном issue;
- PR закрыт;
- исходная ветка PR находится в другом репозитории;
- текст не совпадает с разрешённой командой;
- автор комментария не является участником репозитория.

### 4.2. Формат команды

Допускается только точное совпадение нормализованного текста с одним из двух значений:

- `run build core`;
- `run build telegram`.

Имя сервиса нельзя напрямую подставлять из текста комментария в shell-команды. После разбора оно должно отображаться через жёсткий белый список на заранее известные значения:

| Команда | Dockerfile | Docker Hub repository | Compose service |
| --- | --- | --- | --- |
| `run build core` | `apps/core/Dockerfile` | `marianna2710/receipt-tracker-core` | `core` |
| `run build telegram` | `apps/telegram/Dockerfile` | `marianna2710/receipt-tracker-telegram` | `telegram` |

Дополнительные аргументы, shell-символы, несколько команд в одном комментарии и неизвестные имена отклоняются.

### 4.3. Проверка участника

Под «любым участником» на первом этапе понимаются авторы комментария с GitHub `author_association`:

- `OWNER`;
- `MEMBER`;
- `COLLABORATOR`.

Статусы `CONTRIBUTOR`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN` и `NONE` не дают права на деплой. Если в будущем потребуется более точная модель доступа, проверку следует заменить запросом фактического repository permission через GitHub API.

### 4.4. Выбор исходного кода

После проверки команды workflow получает через GitHub API:

- номер PR;
- состояние PR;
- имя исходного репозитория;
- имя исходной ветки;
- точный `head.sha`.

Сборка выполняется только из неизменяемого `head.sha`, полученного для PR. Это исключает случайную сборку default branch и позволяет связать образ с конкретным коммитом.

Нужно учитывать гонку: после публикации команды в ветку PR может прийти новый push. Поэтому в статусном комментарии и тегах образа указывается SHA, который фактически был собран. Повторная сборка нового коммита запускается новой командой.

### 4.5. Docker-образы и теги

Для каждого успешного билда предлагается публиковать два тега одного образа:

1. Неизменяемый тег для аудита и возможного отката: `pr-<PR_NUMBER>-<SHORT_SHA>`.
2. Подвижный тег тестового окружения: `test`.

Примеры репозиториев:

- `marianna2710/receipt-tracker-core`;
- `marianna2710/receipt-tracker-telegram`.

Серверный Compose использует тег `test`. Неизменяемый тег сохраняется в Docker Hub, чтобы было понятно, какой commit был опубликован, и чтобы при необходимости можно было вручную откатиться.

Перед реализацией следует проверить текущие Dockerfile и при необходимости адаптировать их для CI и production-запуска:

- гарантировать воспроизводимую установку по `pnpm-lock.yaml`;
- не переносить секреты в build context или слои образа;
- добавить корректный `.dockerignore`;
- по возможности отделить стадию сборки от минимального runtime-образа;
- запускать Node.js не от root;
- сохранить отдельную сборку `core` и `telegram`.

Оптимизация Dockerfile полезна, но не должна менять архитектурные границы приложений.

### 4.6. Серверный Docker Compose

В `/home/buho` на сервере должен находиться Compose-файл, описывающий:

- `core` с образом `marianna2710/receipt-tracker-core:test`;
- `telegram` с образом `marianna2710/receipt-tracker-telegram:test`;
- PostgreSQL и будущие базы данных;
- постоянные volumes для данных;
- внутренние Docker networks;
- `depends_on` и healthcheck базы данных там, где сервис действительно зависит от БД;
- restart policy для долгоживущих контейнеров;
- переменные окружения без секретных значений в самом Compose-файле.

Секреты приложения и базы данных должны находиться в защищённом серверном env-файле с ограниченными файловыми правами. GitHub Actions не должен каждый раз перезаписывать этот файл.

При деплое выбранного микросервиса сервер должен:

1. перейти в заранее заданный каталог `/home/buho`;
2. скачать новый образ выбранного сервиса;
3. запустить или пересоздать выбранный сервис через Compose;
4. разрешить Compose поднять объявленные зависимости сервиса, если они остановлены;
5. не удалять volumes и не пересоздавать базу данных без необходимости;
6. вывести состояние Compose-сервисов в лог workflow.

Для выполнения требования о запуске БД нельзя использовать режим, отключающий зависимости. Связь микросервиса с нужной БД должна быть явно описана в серверном Compose.

### 4.7. Один общий test-контур и конкуренция запусков

Все операции развёртывания должны использовать одну concurrency-группу тестового окружения. Это не позволит двум workflow одновременно изменять один Compose-проект.

Отмена уже выполняющегося деплоя нежелательна: прерванное обновление может оставить неоднозначное состояние. Очередной запуск должен дождаться освобождения окружения. При реализации также нужно учитывать поведение GitHub для ожидающих запусков одной concurrency-группы и считать последнюю явно запрошенную сборку целевым состоянием окружения.

## 5. GitHub Secrets и Variables

Рекомендуется создать GitHub Environment с именем `test` и хранить чувствительные значения в его Secrets. Ручное подтверждение Environment не требуется, потому что деплой разрешён любому участнику репозитория, прошедшему проверку workflow.

Предлагаемые Secrets:

| Имя | Назначение |
| --- | --- |
| `DOCKERHUB_TOKEN` | Access token Docker Hub с минимально необходимым правом записи образов |
| `SSH_PRIVATE_KEY` | Отдельный приватный ключ CI/CD для подключения к тестовому серверу |
| `SSH_KNOWN_HOSTS` | Зафиксированный host key тестового сервера |

Предлагаемые Variables:

| Имя | Значение или назначение |
| --- | --- |
| `DOCKERHUB_USERNAME` | `marianna2710` |
| `SSH_HOST` | DNS-имя или IP тестового сервера |
| `SSH_PORT` | SSH-порт, обычно `22` |
| `SSH_USER` | Пользователь SSH; нужно подтвердить при реализации |
| `DEPLOY_PATH` | `/home/buho` |
| `COMPOSE_FILE` | Имя серверного Compose-файла; нужно подтвердить при реализации |

Если `buho` является именем SSH-пользователя, это следует явно зафиксировать на этапе реализации. Из одного пути `/home/buho` это нельзя считать гарантированным фактом.

## 6. Минимальные разрешения workflow

Для `GITHUB_TOKEN` нужно задать явные минимальные permissions:

- чтение содержимого репозитория для checkout;
- чтение данных pull request;
- запись комментария к PR, если workflow будет публиковать статус.

Все остальные разрешения отключаются. Внешние actions следует выбирать из доверенных источников и фиксировать на полном commit SHA либо использовать утверждённый механизм блокировки зависимостей GitHub Actions.

## 7. Подготовка сервера

До включения автоматического деплоя нужно вручную выполнить одноразовую подготовку:

1. Создать или выбрать отдельного непривилегированного пользователя для CI/CD.
2. Установить Docker Engine и Docker Compose v2.
3. Дать пользователю только необходимый доступ к Docker и каталогу деплоя.
4. Подготовить `/home/buho` и серверный Compose-файл.
5. Создать защищённый env-файл с паролями БД и настройками приложений.
6. Настроить named volumes для постоянных данных.
7. Один раз авторизовать сервер в Docker Hub, если образы приватные. Предпочтителен read-only токен.
8. Добавить отдельный публичный SSH-ключ CI/CD в `authorized_keys`.
9. Ограничить SSH-ключ и пользователя настолько, насколько позволяет схема эксплуатации сервера.
10. Зафиксировать host key сервера в `SSH_KNOWN_HOSTS`; не отключать проверку host key.
11. Вручную проверить Compose-конфигурацию и первый запуск БД и приложений.

GitHub runner собирает и публикует образ. Сервер только скачивает готовый образ и запускает Compose; исходный код и Docker build на сервере не требуются.

## 8. План реализации

### Этап 1. Уточнение серверного контракта

Перед написанием workflow подтвердить:

- SSH host, port и user;
- точное имя Compose-файла в `/home/buho`;
- приватные или публичные Docker Hub repositories;
- окончательные имена Compose-сервисов;
- переменные окружения production/test-запуска;
- зависимость каждого микросервиса от конкретной БД;
- политику хранения старых immutable-тегов в Docker Hub.

### Этап 2. Подготовка Docker-образов

1. Проверить обе существующие Dockerfile реальной сборкой.
2. Добавить или уточнить `.dockerignore`.
3. При необходимости сделать multi-stage runtime-образы.
4. Проверить запуск контейнеров без секретов, встроенных в образ.
5. Убедиться, что Core получает подключение к PostgreSQL только через runtime environment.
6. Зафиксировать соответствие сервисов, Dockerfile и Docker Hub repositories.

### Этап 3. Подготовка серверного Compose

1. Создать серверный Compose с `image:` вместо локального `build:`.
2. Описать PostgreSQL, volume, healthcheck и зависимости Core.
3. Описать runtime-переменные Core и Telegram.
4. Проверить ручное скачивание образов.
5. Проверить, что запуск одного сервиса поднимает его остановленные зависимости.
6. Проверить, что обновление приложения не удаляет данные PostgreSQL.
7. Задокументировать ручной откат на immutable-тег.

### Этап 4. Создание GitHub Actions workflow

1. Добавить workflow в `.github/workflows/`.
2. Настроить триггер только на создание комментария.
3. Проверить, что комментарий относится к PR.
4. Строго разобрать команду и применить белый список сервисов.
5. Проверить `author_association` автора.
6. Через GitHub API получить PR и проверить его состояние и происхождение ветки.
7. Получить и checkout точный `head.sha`.
8. Настроить Docker Buildx и вход в Docker Hub.
9. Собрать выбранный Dockerfile.
10. Опубликовать immutable-тег и тег `test`.
11. Подключиться к серверу с проверкой host key.
12. Скачать и обновить выбранный Compose-сервис вместе с его зависимостями.
13. Вывести состояние контейнеров без вывода секретных переменных.
14. Опубликовать итоговый комментарий в PR.
15. Добавить общую concurrency-группу для тестового окружения.

### Этап 5. Документация проекта

После реализации обновить:

- `docs/development.md` — команды запуска, GitHub Secrets/Variables, правила команды в PR и серверная эксплуатация;
- `docs/architecture.md` — только если CI/CD вводит новое принятое архитектурное решение;
- `AGENTS.md` — только если изменятся общие правила работы, стек или границы приложений.

Не хранить в документации реальные токены, пароли, приватные ключи, IP при необходимости его скрыть, или содержимое env-файлов с секретами.

## 9. Поведение комментариев в PR

После распознавания корректной команды желательно оставить один стартовый статус с:

- выбранным сервисом;
- коротким SHA;
- ссылкой на workflow run.

После завершения оставить итог:

- успешно ли собран образ;
- какие repository и immutable-тег опубликованы;
- успешно ли обновлён Compose-сервис;
- ссылка на workflow run;
- при ошибке — название этапа без раскрытия секретов.

Некорректные комментарии, не начинающиеся с точной разрешённой команды, можно молча игнорировать. Команды с правильным префиксом, но неизвестным сервисом, лучше завершать понятным сообщением о допустимых значениях.

## 10. Ошибки и откат

- Если Docker build завершился ошибкой, публикация и SSH-деплой не выполняются.
- Если публикация immutable-тега прошла, но публикация `test` не удалась, деплой не выполняется.
- Если SSH недоступен, опубликованный образ остаётся в Docker Hub, а текущее окружение продолжает работать на предыдущем контейнере.
- Если Compose не смог запустить новый контейнер, workflow завершается ошибкой и сохраняет диагностический вывод без секретов.
- Автоматический rollback на первом этапе не добавляется без проверяемого health endpoint.
- Ручной rollback выполняется переключением выбранного сервиса на ранее опубликованный immutable-тег и повторным применением Compose.
- Команды, удаляющие volumes или данные БД, в workflow не используются.

## 11. Проверки

### Проверки репозитория

Перед включением деплоя выполнить:

- `pnpm build:core`;
- `pnpm build:telegram`;
- сборку обоих Docker-образов;
- проверку конфигурации Docker Compose.

Core e2e не следует объявлять успешно пройденным до появления отдельного тестового окружения БД. Если эта проверка запускается, результат нужно сообщать фактически.

### Проверки workflow

Проверить отдельными PR-комментариями:

1. `run build core` от участника — успешная сборка и деплой Core.
2. `run build telegram` от участника — успешная сборка и деплой Telegram.
3. Неизвестный сервис — отказ до доступа к секретам.
4. Комментарий в issue — игнорирование.
5. Комментарий неучастника — отказ до доступа к секретам.
6. Закрытый PR — отказ.
7. PR из другого репозитория — отказ.
8. Новый push после предыдущей команды — сборка только SHA, явно указанного в конкретном запуске.
9. Остановленная БД — Compose запускает её как зависимость Core.
10. Уже запущенная БД — её volume и данные сохраняются.
11. Две почти одновременные команды — деплои не выполняются параллельно.

## 12. Критерии готовности

Задача считается выполненной, когда:

- workflow находится в default branch и реагирует на новые PR-комментарии;
- принимаются только `core` и `telegram`;
- деплой могут запускать только участники репозитория;
- форки отклоняются;
- собирается точный SHA исходной ветки PR;
- образ публикуется в Docker Hub `marianna2710` с immutable-тегом и тегом `test`;
- GitHub Actions подключается к серверу с проверкой host key;
- выбранный сервис обновляется в `/home/buho` через Docker Compose;
- остановленные зависимости выбранного сервиса запускаются Compose;
- существующие volumes БД не удаляются;
- параллельные деплои одного тестового окружения исключены;
- результат виден в PR и логах Actions;
- секреты не появляются в репозитории и логах;
- документация соответствует фактической реализации.
